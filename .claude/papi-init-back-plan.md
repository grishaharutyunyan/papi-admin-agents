## PART P — LOCKED DECISIONS 2026-08-30

| # | Topic | Decision |
|---|---|---|
| P.1 | **Sequencing — built ahead of access-control** | Roadmap order lists access-control (item 2) before papi-init-back (item 3), but there is no technical dependency between them: access-control manages papi-authority's data; papi-init-back only consumes papi-authority's already-built auth/JWKS/token surface. Building it now is approved. |
| P.2 | **Reference source is developer-specific — never hardcode it in checked-in docs** | The dossier originally hardcoded one developer's absolute path to the reference monorepo; that path doesn't exist on other machines (found: it doesn't exist on this one either). **Fixed:** the actual path now lives only in `.claude.local.md` (gitignored, one per developer) — checked-in docs (this file included) reference "the reference monorepo" generically and never assume a specific location. This machine's copy, for the record of what was actually used while planning papi-init-back: `old-papi/{papi-backend-main, rmp-backend-main, cms-backend-main, dmp-backend-main}` (confirmed by `package.json` name fields — `papi-back`, `rmp-back`, `cms-back`, `dmp-back`), no `.git`, no `CLAUDE.md` (the dossier's papi-back convention quotes were already extracted into `papi-authority-tech-plan.md`'s Global Constraints, so this is not a blocker), missing `access-control-backend` and all 8 frontends (irrelevant to this build, relevant when roadmap item 2 starts). **Treat as READ-ONLY**, same rule regardless of where it's checked out. |
| P.3 | **Scope — backend only** | This plan covers `papi-init-back` only. `papi-init-front` gets its own dossier/phases separately, later. |
| P.4 | **Target architecture — thin papi-authority consumer, not a fork of old papi-back's federated model** | Per Dossier A.2 ("one authority, N thin consumers") and Part I (token & request lifecycle). Consequences, all binding for every phase below: **(a)** No local `users`, `user_roles`, `refresh_tokens`, `two_factor_state`, `login_lockouts` tables/entities — identity lives only in papi-authority. **(b)** `POST /api/auth/login`, `/auth/refresh`, `/auth/logout`, `/sso/login` are **proxy** endpoints: the fork adds its own `PANEL_KEY` and forwards to papi-authority, returning its tokens/errors unchanged — mirrors the old `AccessTokenVerifierService` dispatch pattern (Dossier D.1) but as the issuer's actual counterpart rather than a standalone verifier. **(c)** Every authenticated request verifies the RS256 access token **locally** against papi-authority's cached JWKS — **zero papi-authority calls on the hot path** (Dossier Part I). **(d)** Project/permission scoping reads straight off the token's baked `projects` map keyed by `x-project-id`; **no live DB intersection** — Dossier D.1 already notes forks can't reach papi-authority's DB, so TTL + baked claims is authoritative here, not merely defense-in-depth as it was for the old PAT verifier. |
| P.5 | **No local database in Phases 1-7** (locked 2026-08-30 — **P.10/P.11's amendment reverted 2026-08-31, see P.12; this rule is back in full effect**) | The skeleton shipped Phases 1-7 fully stateless: config, JWKS-cache/verification, auth-proxy, guards, health, hardening — no entities, no migrations, no DB principal. Everything that used to live in papi-back's local DB (`users`, `projects`, `user_roles`) now lives in papi-authority (Dossier Part G). **Rejected at the time:** shipping an empty TypeORM DataSource "for convention" — an extra moving part (docker-compose, migration tooling, DB principal) with nothing to migrate. P.10/P.11 briefly amended this (Phase 8, 2026-08-31) but were themselves reverted the same day when it turned out the actual module code was never built — only declared (P.12). |
| P.10 | **Admin's-own local DB — opt-in wiring, empty schema** (locked 2026-08-31, Phase 8 — **REVERTED 2026-08-31, see P.12: never actually built, only declared in `app.module.ts`/`env.schema.ts`/`CLAUDE.md`**) | A single, static TypeORM `DataSource` for whatever local, non-identity business data a forked panel needs (e.g. rmp's own cashbox/promo config) — analogous to what old papi-back called its "admin DB," minus the identity tables that moved to papi-authority. Ships as wiring only: no entities, gated `ADMIN_DB_ENABLED`. `synchronize` is never env-toggleable — always `false`, hard-coded, unlike old papi-back's `DB_ADMIN_SYNCHRONIZE` env footgun (Dossier D.3b-adjacent finding — see module inventory Part R.5 addendum). **Kept in this table as a design record for whoever builds it for real** — the design itself (empty schema, hard-coded `synchronize: false`) is still the right shape if/when this is actually implemented. |
| P.11 | **Per-project external DB — opt-in, dynamic, cached** (locked 2026-08-31, Phase 8 — **REVERTED 2026-08-31, see P.12: never actually built, only declared**) | Old-papi's `connections/db-connections/{main,bet-data}` pattern, generalized: one backend process serves many projects, each backed by its own physical database (same host, different schema — `main-db`'s shape; or a genuinely different host per project via a URL map — `bet-data-db`'s shape). Connections are opened lazily per project and cached with idle-eviction (ported from old-papi, a real and sensible pattern for this problem, not added complexity) — you cannot statically declare N `DataSource`s at boot when N is "however many projects currently exist" in papi-authority. Gated `EXTERNAL_DB_ENABLED`. **Old-papi's `queryData(dbName, sqlQuery: string)` — a raw-SQL-string interface method — is NOT ported** (module inventory Part R.5 addendum): it was never actually called anywhere in the real code (dead, unsafe surface), and exposing it here would reopen the same injection-shaped risk already closed for ClickHouse in Phase 6. Only `getRepository(dbName, entity)` (parameterized TypeORM access) ships. **Kept in this table as a design record** — same reasoning as P.10. |
| P.6 | **Client-IP passthrough for audit fidelity — flagged, not solved in v1** | Because login is proxied through the fork backend, papi-authority's audit/lockout would otherwise see the fork server's egress IP, not the real end user's. The fork must set `X-Forwarded-For` to its own resolved `req.ip` when calling papi-authority, and papi-authority's `TRUSTED_PROXY_HOPS` needs to account for the extra hop once a fork sits in front of it in a real environment. **Not a v1 blocker** — both services run at `TRUSTED_PROXY_HOPS=0` locally today — but must be revisited together the first time either service is deployed behind the other for real. |
| P.7 | **Panel identity is a dev-bootstrap dependency across two repos** | papi-init-back needs a `PANEL_KEY` env var matching a seeded `admin_panels.key` row in papi-authority's DB, plus that row's `basic_auth_enabled=true` for password-mode dev login (Dossier Part 0.5). Dev setup for this service therefore requires a running, seeded papi-authority instance with a matching panel row — document this explicitly in both services' `.env.example`/README, not just here. |
| P.8 | **App-init (pre-login panel config) needs a new papi-authority endpoint — logged as Dossier 0.61** | The old platform's login page always called `GET /api/configs/app-init` (`@Public()`) first, to know whether to draw password fields, an SSO button, or both, and which Azure tenant/client to use — confirmed present in **every** old fork (`papi-back`, `rmp-back`, `cms-back`, `dmp-back`), so this is not optional to replicate. papi-authority has all the underlying data (`admin_panels.basic_auth_enabled/sso_auth_enabled/sso_tenant_id/sso_client_id` + `platform_settings` default, resolved today by `PanelSsoConfigService`) but **no public route serves it**. Fix lives in papi-authority (0.61: new `GET /api/app-init?panelKey=`), not here — papi-init-back's own `/api/app-init` (Phase 1) is a pure proxy to it. |
| P.9 | **Project-switcher display data needs a new papi-authority endpoint — logged as Dossier 0.62** | The old `/user/me` returned each of the caller's projects as `{id, project, name, theme, logoUrl}` for the switcher UI. The new access token deliberately carries only `{pages, apis}` per project id — no display fields — and papi-authority's `GET /users/me` (0.45) returns profile only, no projects; the only endpoint with project display columns is the platform-admin-only `GET /projects`. Fix lives in papi-authority (0.62: new self-scoped `GET /api/users/me/projects`) — papi-init-back's `/api/users/me/projects` (Phase 5) proxies it. |
| P.12 | **`GET /api/app-init` wrongly shared the tight `auth` throttle bucket — fixed 2026-08-31; and Phase 8 (P.10/P.11) reverted the same day — it was never actually built** | **(a) Throttle fix:** the Phase 7 hardening sweep's checklist listed `GET /api/app-init` alongside actual credential-verifying routes (login/refresh/logout/SSO-login/password-change) as intentionally carrying `@AuthThrottle()`, and treated that as a confirmed-correct finding. It was itself the bug: `app-init` is a read-only, unauthenticated config probe fired on every login-page load, not a credential-verification attempt, so a shared IP with >10 people loading a login page within 60s got 429s on the endpoint deciding whether to even render a password field — a self-inflicted DoS on the login page, not a defense against credential-guessing. Same root cause and same fix as papi-authority's own equivalent route (dossier 0.65, found first via `/code-review` there, then applied here on request). Fixed: removed `@AuthThrottle()` from `AppInitController.getConfig()`; the route now uses the global `default` bucket. **(b) While verifying the fix, `npm run typecheck`/`build` were found broken** — `src/app.module.ts` imported `AdminDbModule`/`ExternalDbModule` from `src/connections/admin-db/` and `src/connections/external-db/`, and `src/configs/env.schema.ts` imported an `ExternalDbMode` enum member, none of which exist anywhere on disk. Grepping the whole `src/` tree found exactly two files referencing them (`app.module.ts`, `env.schema.ts`) and zero implementation files — Phase 8 (P.10/P.11) was documented as shipped (`CLAUDE.md`, this dossier) but the actual module code was never written, only declared. **Fixed on request:** removed the two imports/registrations from `app.module.ts`; removed the `ADMIN_DB_*`/`EXTERNAL_DB_*` fields, the `ExternalDbMode` import, and the now-dead `validateExternalDbUrlMap` cross-field check from `env.schema.ts`; deleted `test/env-schema-db.test.js` (tested only those removed fields — 6 of its tests were failing pre-fix, confirming they exercised the dead fields rather than something newly broken). Also removed the now-fully-unused `typeorm`/`mysql2`/`@nestjs/typeorm` dependencies from `package.json` (confirmed by grep: nothing under `src/`/`test/` imports any of them once the two connections modules were gone) and ran `npm install` to sync `node_modules`/`package-lock.json`. Also fixed 2 pre-existing, unrelated Prettier formatting errors in `src/configs/index.configs.ts`/`src/constants/enums/config.enums.ts` (`eslint --fix`) to get `npm run lint` clean. **Verified:** `npm run typecheck`/`lint --max-warnings 0`/`build` all clean; `npm test` 82 pass / 0 fail / 1 skipped (the skip predates this change). P.5's "no DB in v1" is back in full effect; P.10/P.11 are kept in the table above as a design record only, not as shipped state. **If Phase 8 is wanted again, it must be built for real** — code, tests, and docs together, verified the same way every other phase in this dossier was, not re-declared in `CLAUDE.md` alone. |

| P.13 | **Read-only `GET /api/users` (list) proxy added — locked 2026-08-31, post-v1** | Deliberate, user-approved scope addition to a service whose P.4/P.5 say "no local identity, ever": the override is that this holds **no table** — it's a pure stateless proxy to papi-authority's `GET /api/users`, i.e. case 1 of the "no local identity" carve-out in `papi-init-back/CLAUDE.md` (proxying), the same category `/api/auth/*`/`/api/sso/*`/`/api/users/me*`/`/api/app-init` already fall into. Needed for admin-panel user-listing UIs (a forked panel's user-management screen needs a list before it needs anything else). Deliberately scoped to **list only** — `UserQueryDto` (page/limit/search/order/roleId/isActive), `UserView`/`PaginatedUserView` runtime-guarded response, gated `@PlatformPermissions(['users', 'view'])` (not `@SkipPermissions()` — this is an admin listing of other users, not a self-resource). **Rejected alternative:** proxying the rest of papi-authority's `UsersController` (create/update/delete/access/password/unauthorize) — rejected, that surface stays access-control's per papi-authority's own controller comment ("the surface access-control consumes"); a future task adding any of it needs its own explicit approval, this addition does not imply it. Implementation: `src/api/users/dto/user-query.dto.ts`, `src/api/users/dto/user-view.dto.ts`, `src/api/users/controllers/users.controller.ts`, `src/api/users/services/users.service.ts`, `src/core/http/transforms.ts` (query-string boolean transform, copied from papi-authority's own `src/core/http/transforms.ts`), registered in `src/api/users/users.module.ts` alongside `MeController`/`MeService`. |

## Cross-service dependency

Phases 1 and 5 of `papi-init-back-tech-plan.md` cannot be exit-criteria-complete until papi-authority
ships 0.61 and 0.62 respectively. Recommendation: implement each papi-authority endpoint as its own
small phase there, timed just ahead of the corresponding papi-init-back phase — both are additive
(new routes, no schema/migration, no change to existing grants) and low-risk relative to the rest of
papi-authority's build.

---

## Later phases (explicitly OUT of v1 — do not start)

Business-domain modules (projects/limits/operators/blockers CRUD, any panel-specific resource) —
those belong to whichever real panel forks this skeleton, not to the skeleton itself. Frontend
wiring is `papi-init-front`'s scope (P.3). SSO with real Azure values, per P.6/P.7's cross-service
follow-ups, and access-control integration all wait on their own roadmap items.
