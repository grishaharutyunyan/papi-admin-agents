| 0.25 | **Console DB user gets operation-scoped auth-runtime grants — B.3 preserved** (locked 2026-08-05, refines B.3 + Part G) | `papi_console` is **not** granted blanket access. | 0.27 | **Identifier storage** (locked 2026-08-05, resolves the Phase 2 kickoff question) | UUIDv7 identity PKs are stored as **`CHAR(36)`**, not `BINARY(16)`. Rationale: the DB team is external (0.26) and runs incident-response SQL by hand — `WHERE id = '…'` must just work; a `ValueTransformer` bug on an identity PK is a catastrophic silent failure; and scale is admin-tier. **High-volume auth-runtime tables (`auth_audit_events`, `refresh_tokens`) use `BIGINT UNSIGNED AUTO_INCREMENT` PKs** — those rows are never addressed by an external client (a refresh token is identified by its secret, audit rows only through an admin-only filtered API), so B.9's anti-enumeration rationale does not apply and the largest tables stay compact. UUIDv7 generation needs the `uuid` package (Node's `crypto.randomUUID()` is v4 only). ⚠ If ever revisited: `UUID_TO_BIN(x, 1)` must **not** be used — the swap flag is for UUIDv1 and destroys UUIDv7's time-ordering. |
| 0.28 | **Audit retention — deferred, but designed for** (noted 2026-08-05) | Not in v1. | 0.29 | **Soft delete scope + the burned-email problem** (locked 2026-08-05) | Soft delete (`deleted_at datetime(6)`) applies to **identity tables only**. Auth-runtime uses explicit lifecycle columns instead (`revoked_at` per 0.25) and hard-deletes where the design says so (invitations at approval, 0.24). **Uniqueness must discriminate on a generated marker column, NOT on `deleted_at`.** ⚠ **Corrected 2026-08-05 after testing against MySQL 8.4** — the original form `UNIQUE (email, deleted_at)` recorded here **enforces nothing**: MySQL treats NULLs as *distinct* in a unique index, so two live rows both holding `deleted_at = NULL` do not collide. A duplicate live email was accepted in a live test. The working form is a generated stored column on every soft-deletable table — `deleted_marker VARCHAR(36) GENERATED ALWAYS AS (IF(deleted_at IS NULL, '', id)) STORED` — with `UNIQUE (email, deleted_marker)`. Live rows all carry `''` so duplicates collide; each tombstone carries its own id so any number may share a value. This preserves TypeORM's `@DeleteDateColumn` semantics (which test `deleted_at IS NULL`) while actually enforcing one live row per value. papi-back's plain `UNIQUE` + soft delete **permanently burns a user's email/username/`oid`**, making re-invitation impossible (verified, D.3c). The auth engine must additionally filter deleted users explicitly so a tombstoned account can never authenticate. |
| 0.30 | **Permissions are stored as normalized rows, NOT JSON** (locked 2026-08-05) | `project_entitlements` (L2) and `user_project_permissions` (L4) are relational rows keyed by `(section, key, kind)`, not `IMetaPermissions` JSON blobs. Rationale: the resolver bakes permissions into tokens either way, so query speed is not the driver — **auditability is**. "Which users can do X?" is a question auditors ask; under JSON it is a full scan over opaque data with no guarantee the section/action even exists. A **`permission_catalog`** table (seeded from the Phase 5 code catalog) gives real referential integrity: entitlements and overrides carry foreign keys into it, so an entitlement naming a non-existent permission becomes impossible rather than merely unlikely. This also sidesteps the fork-portability defect where papi-back writes `"usersSection"` and rmp writes `"users"` for the same section (D.3c). |
| 0.31 | **2FA secrets encrypted at rest; and a general "strong schema" mandate** (locked 2026-08-05) | `two_factor_state.secret_encrypted` is stored **encrypted** (AES-GCM), never plaintext, with `select: false` and a `key_version` column so rotation is possible. papi-back stores TOTP secrets in plaintext and loads them on every user read — a DB dump there yields permanent second-factor bypass. Encryption is wired with the key provider in Phase 3/4; Phase 2 creates the columns. **General mandate from the user:** build the schema "the full best way" — every foreign key declared with an explicit `ON DELETE`/`ON UPDATE`, every FK column indexed, every domain-unique column actually `UNIQUE` (`projects.project`, `projects.project_db`, `admin_panels.key`, `user_roles.name`, `project_limits(project_id,currency)`, `project_operators(project_id,op_name)` — all missing today), composite indexes for the real query paths, `NOT NULL` + sensible defaults wherever the domain allows, `datetime(6)` UTC for every instant (never MySQL `TIMESTAMP`, which has a 2038 ceiling and implicit session-timezone conversion), and no `eager: true` relations. |

| 0.32 | **The signing key NEVER leaves Azure Key Vault — remote signing** (locked 2026-08-05, Phase 3 kickoff) | papi-authority does **not** download the RS256 private key. It sends the SHA-256 digest of each JWS signing input to Key Vault's `CryptographyClient.sign('RS256', digest)`; the signature is produced **inside the vault**. Rationale (B.4 calls the key "the crown jewel"): this is the only design where compromising the papi-authority process does not yield the key. Under a download-to-memory design an attacker exfiltrates it once and can mint tokens for any user **forever, undetectably, even after eviction**; under remote signing they can only request signatures *while* they hold the process, and revoking the app's Key Vault access stops it immediately. **Accepted cost, explicitly:** Key Vault becomes a hard dependency for every login and refresh. Throughput is a non-issue (~2 signs/sec against a ~200/sec limit), and a vault outage does not break the platform — the forks verify locally against cached JWKS (B.7) and existing access tokens remain valid to their TTL — but **no new sessions can be issued while it is down**. **Consequence:** no JWT signing library is used. Remote signing cannot go through `jsonwebtoken.sign()` (it wants a local key), so the JWS compact serialization is assembled directly per RFC 7515 — which also sidesteps `jose@6` being ESM-only in a CommonJS build. Every emitted token is cross-verified against `jsonwebtoken.verify()` in tests so an independent implementation confirms the output. |
| 0.33 | **The key provider is a DI-enforced boundary** (locked 2026-08-05) | `KeyProvider` is provided inside `src/core/crypto/` and **deliberately not exported** from `CryptoModule`; only `TokenSignerService` crosses the module boundary. No other module in the service can inject the key provider — the "private key never leaves this module" rule is enforced by the DI container, not by convention. Location is `src/core/crypto/` (infrastructure, alongside `errors/`, `health/`, `shutdown/`) rather than `src/api/` — nothing CRUDs a key, so it is not a domain. |

| 0.34 | **Password hashing = argon2id via Node's built-in `crypto.argon2`** (locked 2026-08-06, supersedes the tech plan's "bcrypt") | Node 24 ships `crypto.argon2` / `argon2Sync` — verified working with no experimental warning. **argon2id, not bcrypt:** it is OWASP's current first choice, and bcrypt silently truncates passwords at 72 bytes, which is a real footgun for passphrases. **Built-in, not the `argon2` npm package:** it keeps a native addon out of the identity core, and this project has already been bitten twice by dependency packaging (`jose` and `uuid` are both ESM-only in a CommonJS build). Parameters: `m=65536, t=3, p=4, tagLength=32`, 16-byte random salt. **Accepted cost:** the standard PHC string (`$argon2id$v=19$m=…,t=…,p=…$salt$hash`) is encoded/decoded by us — that is formatting, not cryptography, since the KDF is Node's — and our output is cross-verified against the `argon2` npm package (devDependency only) so an independent implementation confirms the hashes are standard and interoperable. Verification uses `timingSafeEqual`. `users.password` is already `varchar(255)`, which fits the encoded form with headroom. |

# PART A — WHY (Context & Goal)

## A.1 The problem

The monorepo is **8 NestJS backends forked from `papi-back`** with matching React/Vite frontends. Today **every fork owns its own copy** of `users`, `user-roles`, `projects`, and a full login/JWT/guard stack. Consequences:

- A person who needs RMP + CMS + DMP must **authenticate (and be auto-created) separately in each system**. Identity is duplicated N times.
- No single source of truth for "who is this user and what can they do" → drift + privilege-escalation risk.
- Project config (limits, operators, etc.) lives only in whichever fork needs it (rmp), not centrally.

## A.2 The goal

Invert the federated model into **one authority, N thin consumers**. Build **`papi-authority`**: the single source of truth for identity + authorization, and the **only** service on the platform that holds a signing key and issues tokens. Built **from scratch**, security-first (government/secret-grade posture — the user's explicit framing: *"very secure very strong… government project… full security coverage… latest node/nestjs, most best practice"*).

## A.3 Scope of THIS plan (v1)

**In scope:** `papi-authority` only — its owned database (the source of truth) + the full auth/token-issuance/authorization engine + identity CRUD API + onboarding endpoints + a minimal standalone join page + audit + hardening.

**Out of scope (later phases):**
- Retargeting `access-control` (back + front) to be papi-authority's admin console.
- Wiring the forks (rmp first) to consume papi-authority tokens (fork-side guard swap).
- Deleting the `users` block from fork frontends.
- The numeric→UUID data migration inside each fork.
- The richer admin UI (papi-authority exposes endpoints; access-control renders later).

- Service `papi-back/src/api/auth/services/auth.service.ts`:
  - `loginValidation`: case-insensitive username/email lookup; rejects SSO-only accounts (has `oid`); bcrypt compare; **account lockout** (10 failures/15 min → 30-min lock via `loginFailureCount`/`lastFailureAt`/`lockedUntil`); optional 2FA (`TwoFactorService`).
  - `issueTokens`: signs session JWT (`sub`, `username`, `language`, `email`, random `jti`) via `@nestjs/jwt`; plus rotating opaque refresh token.
  - **Refresh tokens:** random 48 bytes, stored **SHA-256-hashed** in `refresh_tokens` with a `familyId`; rotation on refresh with **reuse-detection** (revokes whole family + audit event). Entity `papi-back/src/api/auth/entities/refresh-token.entity.ts`; service `papi-back/src/api/auth/services/refresh-token-entity.service.ts`.

**Session JWT verification — `papi-back/src/guards/jwt.guard.ts`:**
- Reads `Authorization: Bearer <token>` + `x-project-id`. `@Public()` → skip; `@WithoutProject()` → auth but no project.
- **Dispatches by token shape:** if `AccessTokenVerifierService.isAccessToken(token)` (prefix `papi_pat_`) → PAT path; else session JWT → `authService.verifyJwt` → `authService.getUser(sub, username)` loads user with `projects` + `role` (active only), strips `password`/`twoFASecret`/`updatedAt`, sets `request.user`; loads `request.project` unless `@WithoutProject()`. Any failure → uniform 401.

**SSO (Azure AD) — `papi-back/src/api/sso/`:** `POST /api/sso/login` (`@Public()`). `sso.service.ts` verifies Azure token signature against JWKS (`jwks-rsa`), matches user by `email`+`oid`. First-time SSO users auto-created `isActive:false` (await admin approval), empty permissions; returns empty access_token until activated.

**The RS256 PAT verifier (the pattern to mirror on papi-authority's ISSUER side) — `papi-back/src/api/access-tokens/`:**
- papi-back **only verifies**, does not issue/store PATs (issuance meant to live in access-control, but doesn't exist yet — see E.3).
- Wire format: `Authorization: Bearer papi_pat_<JWS>` where `<JWS>` is RS256-signed. Prefix `PAT_TOKEN_PREFIX = 'papi_pat_'`.
- `AccessTokenClaims` (`.../interfaces/access-token-claims.interface.ts`): `iss`, `aud`, `exp`, `iat`, `jti`, `type:'pat'`, `userId` (nullable — null = global/service token), `permissions` (IMetaPermissions), `allProjects` (bool), `projects: number[]`.
- `verify()` (`.../services/access-token-verifier.service.ts`): (1) require configured public key (env `PAT_VERIFICATION_PUBLIC_KEY_BASE64`); (2) strip prefix, `jwt.verify` `algorithms:['RS256']` + issuer + audience; (3) validate `type==='pat'` + `jti`; (4) optional **Redis denylist** `pat:revoked:<jti>` (env-gated); (5) user-bound tokens load live active user + **intersect** token perms ∩ user effective perms and token projects ∩ user projects (defense-in-depth); (6) global tokens: claims authoritative; (7) builds a `UserEntity`-shaped synthetic context with `role: undefined`, `meta.permissions` = effective, markers `__authType:'pat'`, `__tokenJti`, `__allProjects`. Helpers in `.../helpers/permissions-intersect.helper.ts`.
- **Note for papi-authority:** the forks can't reach papi-authority's DB, so the fork tokens rely on **TTL + baked claims** (not a live DB intersection). The intersection trick only works inside a service that shares the identity DB.

**Other guards (manual `@UseGuards`):** `papi-back/src/guards/two-factor.guard.ts`, `.../external-system-auth.guard.ts` (compares `apikey` header to `EXTERNAL_SYSTEM_AUTH_API_KEY`).

## D.3b papi-back baseline defects — verified 2026-08-05 (do NOT port these)

Extracted by Atlas from the read-only reference monorepo and cross-checked against an empirical build probe. **papi-back is a weaker baseline than Parts B.12 / O.1 imply** — treat it as the pattern source, never the security ceiling (Part 0.3 already says "verify each piece is 100% secure and current best practice"; these are the specific failures that check must catch). The full carry-forward vs improve table is in the tech-plan's Phase 1 "Deliberate divergences" section.

**Security-relevant:**
- **Spoofable client IP.** No `app.set('trust proxy', …)` anywhere in `papi-back/src/main.ts`, and `src/common/helpers/getIp.ts` blindly trusts `x-forwarded-for`. Because the global `ThrottlerGuard` is IP-keyed and the audit trail records the same value, **an attacker controls both their own rate-limit bucket and the IP written to audit rows.** This directly defeats the Part M audit assertions and the Part 0.10 lockout design.
- **Unauthenticated infra disclosure.** `/metrics` is `@Public()` (Prometheus, with `route: req.originalUrl` → unbounded label cardinality and IDs/query strings leaked into labels); `/ready` returns raw DB `e.message` text to anonymous callers.
- **Dead Key Vault path.** `src/configs/bootstrap-secrets.ts` is **never called** — grep over `src/`, `scripts/`, `package.json` finds only its definition. **Phase 3's Key Vault wiring is net-new; there is nothing to port.**
- **Convention without enforcement.** "Never access `process.env` outside `src/configs`" is documented in `papi-back/CLAUDE.md` L166 only — no ESLint rule, no CI check, and 5 files violate it (`main.ts`, `typeorm-cli-data-source.ts`, `connections/db-connections/index.ts`, `connections/gateways/index.ts`, `services/messaging/messaging.module.ts`).
- **Non-strict TypeScript.** `strictNullChecks:false`, `noImplicitAny:false`, `strictBindCallApply:false`, `@typescript-eslint/no-explicit-any:'off'`, and zero type-aware lint rules despite `parserOptions.project` being set.
- **Vulnerable/phantom deps.** `xlsx@^0.18.5` is the npm-registry copy with known unpatched prototype-pollution/ReDoS advisories (SheetJS moved off npm) — **do not carry into papi-authority**. `dotenv` is imported by `src/typeorm-cli-data-source.ts` but undeclared, resolving only transitively via `@nestjs/config`.
- CSP allows `'unsafe-inline'` in `scriptSrc`; Swagger basic-auth uses hardcoded username `simba`.

**Correctness:**
- **Broken build output.** No `rootDir`/`include`, so `scripts/*.ts` are compiled too and output lands at `dist/src/main.js`. Both `npm run start:prod` (`node dist/main`) and the Dockerfile `CMD ["node","dist/main.js"]` are therefore broken as written. `EXPOSE 3000` also contradicts the config default port `7772`.
- **Duplicate health routes.** `/live` and `/ready` are registered in **both** `src/app.controller.ts` and `src/metrics/controllers/metrics.controller.ts` — whichever module resolves first wins. The `AppController` variant returns HTTP **200** with a body containing `statusCode: 503` while shutting down.
- **Shutdown does not drain.** `GracefulShutdownService.markShuttingDown()` is followed immediately by `app.close()` + `process.exit(0)` — no grace window for a load balancer to observe `/ready` flipping, no in-flight tracker, no `app.close()` timeout guard.
- **`RouterModule` triple-listing.** Every domain module is listed 3× in `src/api/api.module.ts` (RouterModule children + `imports` + `exports`); papi-back's own CLAUDE.md L180 flags that omitting one silently drops the `/api` prefix. There is no API versioning at all.
- Entity-services from other domains are re-declared as providers inside `AuthModule`, producing duplicate provider instances per module.
- `test:e2e` points at `./test/jest-e2e.json`; **no `test/` directory exists**.

**`papi-back/CLAUDE.md` is stale vs its own code** — do not read it as current state: it claims a 20 MB body limit (actual `100kb`), open CORS `origin:'*'` (actual: allow-list callback), two global guards (actual: **three**, Throttler first), `JWT_SECRET`/`DB_ADMIN_SYNCHRONIZE` as required env (both removed), and config living in `index.configs.ts` (now a merge shim over per-domain files).

**Genuinely worth carrying forward:** the `<NS>_<KEY>_ENABLED` env-gating pattern and dynamic module loading; `ClsModule` request-id with inbound `x-request-id` reuse + response echo; `APP_GUARD` order Throttler → Jwt → Permission; the RFC-9457 `problem+json` exception filter + `BusinessError`; the redaction key list and auth-path body blanking (as a *spec* for the company logging package, Part 0.15); `synchronize:false` + the prod-like startup guard; the RS256 `JwtModule` factory that throws at startup when keys are missing; docker-compose's `${VAR:?}` required-secret form; husky + lint-staged; multi-stage Dockerfile with `USER node` + HEALTHCHECK.

## D.3c Entity re-verification 2026-08-05 — drift from Part D, and sizing facts

Full re-read of every referenced entity against current code. **Part D's column lists are accurate except where listed here.** Also note: `papi-back` has **no `migrations/` directory at all** despite declaring `migrations:['dist/migrations/*.js']` + `synchronize:false`, and `rmp-backend` still runs `synchronize` from env — so **there is no DDL artifact anywhere in the monorepo**; entity metadata is the only authority.

**Semantics Part D got wrong — these change the target design:**
- **Role permissions REPLACE user permissions; they never merge.** `papi-back/src/guards/permission.guard.ts:107-111`: `user.role?.id ? user.role.permissions[section] : user.meta?.permissions[section]`. If a user has **any** role, `users.meta.permissions` is **dead data**. Our 4-layer model `(L2 ∩ L3) − L4` is a deliberate departure — L4 subtracts from the role grant rather than being an ignored fallback. State this explicitly wherever L4 is implemented, or someone will "restore" the old behaviour.
- **The same logical section has different JSON keys across forks:** papi-back writes `"usersSection"`, rmp writes `"users"`. Stored permission blobs are **not fork-portable**; the central catalog must normalize, and no fork's blob can be copied verbatim.
- **`users.meta` and `user-roles.permissions` hold the same data at different nesting depths** (`{permissions:{…}}` vs `{…}` at top level).

**Column-level drift:**
- `users.twoFASecret` — the DB column is literally **`twoFASecret`** (camelCase): the `@Column` has no `name:` and **no fork configures a naming strategy**, so property names leak into the schema. Its two siblings *do* set `name:`. Part D's `two_fa_secret` is wrong.
- `users.uid` is `varchar(36)` and is **neither unique nor indexed** — every external lookup by it is a full scan and nothing prevents collisions.
- `projects.restore_bet_history_days_count` also carries the `parseFloat` transformer (Part D omits it) — without it the value returns as a string.
- `project_operator_op_types.currencies` has **no `length`**, so MySQL materializes `varchar(255)` — a real capacity cap (~40 currency codes), not a detail.
- `project_blockers`' `toSnakeCase` transformer only accepts **strings** and would throw on the object/array values both its columns hold. Latent only because there is no write path. **Do not port it.**
- `users_invite` has **no expiry column** and stores the token in **plaintext**.
- Table name is literally **`user-roles`** (hyphenated) — requires backtick quoting forever. Rename to `user_roles`.

**Secret-column sizing for the new schema:**
- `password varchar(100)` fits bcrypt (60 chars) but **does not fit an argon2id encoded hash** (~96–100 and grows with parameters) → size `varchar(255)`.
- TOTP secrets are stored **plaintext base32 with no `select:false`** — loaded on every user read. Encrypted (AES-GCM + IV + tag, base64) needs ~120–180 → size `varchar(255)` **and** `select:false`.
- Refresh `hashed_token varchar(64)` is an exact fit for SHA-256 hex (zero headroom) → use `char(64)`.
- Invite tokens should be **hashed** (`char(64)`), never stored plaintext.

**Structural defects to fix rather than reproduce:** `TIMESTAMP` used for every security-critical instant (`locked_until`, `expires_at`, `revoked_at`, …) → **2038 ceiling + implicit session-timezone conversion**; use `datetime(6)` UTC throughout. `audit_events.id` is **`int`** (2.1 B ceiling) with best-effort error-swallowing writes, no retention, and the two natural query paths (`target_type`+`target_id`, `actor_user_id`+`created_at`) unindexed. `refresh_tokens` has **no FK to `users` and no purge job** → unbounded growth. Missing uniqueness the domain requires: `projects.project`, `projects.project_db`, `admin_panels.key`, `user_roles.name`, `project_limits(project_id, currency)`, `project_operators(project_id, op_name)`. `project_blockers` is `@OneToOne` on one side and `@ManyToOne` with no unique constraint on the other — the DB permits N rows while the app reads one. `eager: true` on `projects.operators`/`.limits` drags every satellite row into nearly every authenticated request.

# PART E — access-control-backend DEEP ANALYSIS (the future console)

**Location:** `access-control-backend`. It is a **management/orchestration layer over the forks' own admin DBs, plus a tiny own central-identity DB.** It is NOT a second full identity store, and it does NOT issue RS256/PAT tokens.

## E.1 What it owns vs what it puppeteers

- **Its own MySQL DB (`databaseAdmin`)** models `users` (`UserEntity`) + `admin_panels` (`AdminPanelEntity`) + a **user↔admin_panels M2M** (`@JoinTable`). Entities registered: `[UserEntity, AdminPanelEntity]` (`access-control-backend/src/configs/global.configs.ts`).
- **For everything else it reaches into each fork's OWN admin DB** via a dynamic per-fork connection (`access-control-backend/src/connections/db-connections/admin/admin-db.connection.ts`, `@Global`). `getConnection(key)` merges a URL-less template `databaseExternalAdmin` with `adminConfigs[key].dbUri` (env `ADMIN_PANEL_<KEY>_DB_URI`, `_DB_SSL`, `_AUTH_KEY`, `_URI`), caches per key, closes idle after 3 min. External entities: `AdminUserEntity` (table `users`), `AdminUserRolesEntity` (table `user-roles`), `AdminProjectsEntity` (table `projects`) under `.../db-connections/admin/entities/`.
- So today **each fork still owns its own users/projects/user-roles**; access-control just does remote CRUD into them. `admin-panel-projects` even has an `RMP` special-case branch (`getByIdCustom`/`updateCustom`).

## E.2 Domain modules & routes (all under `/api`, guards `JwtGuard`→`PermissionGuard`)

- `auth` — `POST /api/auth/login` (basic-auth-gated middleware) → local `users`, bcrypt, block `oid`, `isActive` → **HS256 JWT**. Service `.../src/api/auth/services/auth.service.ts`.
- `sso` — `POST /api/sso/login` → Azure verify via `jwks-rsa` → auto-provision inactive local user → HS256 JWT. `.../src/api/sso/services/sso.service.ts`.
- `configs` — `GET /api/configs`, `GET /api/configs/app-init` (`@Public`), `GET /api/configs/permissions`. `getPermissions()` **HTTP-federates** to each fork's `GET /api/external-system/configs` with the fork's `authKey` — the permission catalog is owned by each fork, not access-control.
- `users/user` (self) — `GET/PATCH /api/user/me` (returns user + `adminPanels` + `meta.permissions`).
- `users/users-section` (identity admin) — `GET/POST/PUT/DELETE /api/users[/:id]` — manages the **local central `users`** + panel assignment + `meta.permissions`. Guard section `USERS_SECTION`.

- `admin-panel-projects` (path `admin-projects`) — CR-U (no delete) into fork's `projects`. Guard `ADMIN_PANEL_PROJECTS`.

## E.3 CRITICAL: no token issuance exists anywhere yet

- access-control has **no RS256 signing, no key-pair, no `.pem`, no `jsonwebtoken.sign`, no `papi_pat_`, no PAT, no JWKS/public-key endpoint, no token/session/PAT table.** Only **HS256 session JWT** via `@nestjs/jwt` (symmetric `JWT_SECRET`), same as forks. `jwks-rsa` present only for **inbound Azure verification**. Deps: `@nestjs/jwt`, `@nestjs/passport`, `passport-jwt`, `passport-http`, `bcrypt`, `jwks-rsa` (no `jsonwebtoken`, no `jose`).
- papi-back is only the **verifier**. **⇒ RS256/PAT/JWKS issuance is net-new work in papi-authority — nothing to copy an issuer from; the verifier is the reference for claim shape.**

# PART F — THE AUTHORIZATION MODEL (target design)

## F.1 Current permission system (verified facts)

- **Vocabulary:** `[section, action]` string tuples in an `IMetaPermissions` JSON blob, e.g. `{ transactions: ['view','export',...], account: ['view','edit'] }`.
- **Storage, two places:** on a **role** (`user-roles.permissions`) or as a **per-user override** (`users.meta.permissions`). **Resolution rule: role wins; meta is the fallback for role-less users. No merge, no inheritance.** (Guard: `user.role?.id ? role.permissions[section] : user.meta?.permissions[section]`. Same in `/me`.)
- **Catalog constant:** `permissionsMetaData` (full section→all-actions) + `permissionsMetaDataEmpty` (blank template), in `rmp-backend/src/constants/constants/permission.constants.ts`. **Hand-maintained → drifts** (see F.4).
- **`@Roles()` decorator** (`rmp-backend/src/decorators/roles.decorator.ts`): `RoleTuple=[section,action]`; `PermissionGroup={permissions:RoleTuple[], logic:AND|OR}`; `RoleRequirement` = tuple | tuple[] | group | group[] | **function `(req,body)=>requirement`**. Helpers `RequireAll` (AND), `RequireAny` (OR).
- **`PermissionGuard`** (`rmp-backend/src/guards/permission.guard.ts`, global after `JwtGuard`): (1) unless `@WithoutProject()`, verify `request.project.id ∈ user.projects[].id` (**project membership**, fails closed); (2) read `@Roles`; (3) evaluate (functions invoked with `(request, body)`; multiple `@Roles` args OR'd; bare tuples AND'd; groups by their logic). **Default-deny in papi-back** (no `@Roles`+no `@SkipPermissions` ⇒ Forbidden); **default-ALLOW in rmp** (accidental — any authenticated project member passes) — **fix to default-deny in core**.
- Enforcement is **per-route at the controller** — each route declares its `[section, action]`. Examples: `GET /transactions` → `@Roles([TRANSACTIONS, VIEW])`; `POST /transactions/manual-insert` → `@Roles(RequireAny([[TRANSACTIONS, MANUAL_INSERT_IN],[TRANSACTIONS, MANUAL_INSERT_OUT]]))`; player-limits controller mixes `[GENERAL_LIMIT, view]`, `[INDIVIDUAL_LIMIT, add/edit]`.

## F.4 Frontend gating (verified)

- Permissions from `/me` (`{user, permissions}`, already role-or-meta resolved). Hook `papi-front/src/hooks/useCheckPermission.ts` (typed; two overloads), util `papi-front/src/commons/utilities/permissions.utils.ts` (`hasPermission(perms, section, action)`), types `papi-front/src/constants/types/permissions.types.ts`. **Rule: never call `permissions[section].includes()` directly — always the hook.** (rmp-frontend still uses the raw `.includes()` pattern.)
- Three gating surfaces, same check: **routes** (`rmp-frontend/src/router/Router.tsx` via `<ProtectedRoutes section=... permission=... />`), **sidebar** (`rmp-frontend/src/components/common/SidebarMenu.tsx`, each item's `view: [section, action]`), **buttons/columns**. - **Live drift found:** rmp-frontend `TransactionsPermissionsTypes` is **missing** 5 backend actions (reportIds, transactionsReportsView, transactionsReportsCheck, generateExcel, approveTransactionsReports) — enums are hand-duplicated per side. **papi-authority's central codegen'd catalog eliminates this whole bug class.**

## F.5 The target 4-layer model

Effective access for `(user, project, page-or-api)`, evaluated **in this order** (project gates before user):

```
1. user ↔ project membership   — is the user assigned to this project at all?
2. project entitlement          — does THIS PROJECT have this page/api licensed?   ← gates everyone on the project
3. role permission              — does the user's role allow this page/api?
4. user↔project override        — is this specific user restricted here? (subtract)

effective = (L2 ∩ L3) − L4,   only if L1 holds
```

- Keep the proven `[section, action]` vocabulary. Add **page-keys vs api-keys** under each section so an override can hide a page and/or block an endpoint independently.
- **papi-authority computes L1–L4 once** at token issue / refresh — for **every project the user has** — and bakes a `projectId → {pages, apis}` effective map into the access token. Forks read the token — no per-request math, no DB, no papi-authority call. Switching project just changes `x-project-id`; the fork applies that project's entry from the map.
- **Default-deny** everywhere. **One central catalog** (sections → pages → apis) owned by papi-authority, **codegen-checked** so backend/frontend can't drift.
- Backend code shape is at the implementer's discretion (likely an `authorization` module with a policy/entitlement resolver + a claims-driven guard); the 4-layer semantics are the fixed requirement. Present the concrete design at that build step.

# PART G — TARGET DATA MODEL (papi-authority owns the single source of truth)

Built fresh: **UUIDv7 PKs**, snake_case columns, **TypeORM migrations (no `synchronize`)**, **MySQL** (Part 0.2). Split into two table-groups so the two DB users get clean **table-level** grants.

> **How the two DB users work inside one service (v1):** papi-authority runs **two TypeORM DataSources**. The auth engine (login/refresh/SSO/audit) connects as the **authority** DB user; the identity CRUD module + invitation approval (Part H.6) connect as the **console** DB user — the same account access-control will use later. The grants therefore isolate the modules from each other even inside one process: a bug in the CRUD module cannot touch refresh tokens; a bug in the auth engine cannot create/edit identities.

**Identity tables — console DB user = CRUD; authority DB user = SELECT + the narrow column-UPDATE of 0.23:**
- `users` — base identity superset (D.2 + D.5) + `oid` + `token_epoch` (int, reserved for future freshness) + soft-delete. UUIDv7 PK. **Per Part 0.10 it does NOT carry lockout or 2FA columns** (they live in auth-runtime). **Rows are created ONLY by the console DB user** — at invitation approval (0.8/0.24) or by direct admin creation in password mode (0.18). **Per 0.20/0.23 the authority DB user additionally holds column-level `UPDATE` on `first_name, last_name, phone, language, timezone, password, is_sp_reset, sp_updated_at` — and on nothing else** (never `is_active`, `oid`, or any role/project/panel grant column; never `INSERT`/`DELETE`), so it can serve self-service profile and password changes but can never alter identity or authorization.
- `projects` — the **combined superset** (base 8 + rmp's 7 extras; D.3/D.5). UUIDv7 PK.
- `project_limits`, `project_operators`, `project_operator_op_types`, `project_blockers` — ported from rmp (D.3). Enums `OperatorType`, `RequiredLevel`.
- `user_roles` — unchanged shape (`name`, `public`, `permissions` JSON).
- `admin_panels` — from access-control (`name`, `key`, `is_active`, `theme`) **+ per-panel auth config (Part 0.4/0.5): `basic_auth_enabled` (bool), `sso_auth_enabled` (bool), `sso_tenant_id` (nullable), `sso_client_id` (nullable)** — the SSO columns are **overrides**: NULL → the platform default app (Part 0.9). Managed by access-control later; seeded for dev.
- `platform_settings` — **NEW (Part 0.9)**: single-row, console-managed platform config; holds the platform Azure app's default `sso_tenant_id`/`sso_client_id` (seeded placeholders in dev). Final shape at Phase 2 kickoff.
- `project_entitlements` — **NEW**: per-project licensed page/api map (`IMetaPermissions`-shaped) → **L2**.
- `user_project_permissions` — **NEW**: per-(user,project) override, deny (and optional grant-within-ceiling) → **L4**.
- Grant tables: `user ↔ admin_panels` (which apps a user may open), `user ↔ projects` (**L1** membership), `user → role`.

**Auth-runtime tables — authority DB user = CRUD; console DB user = the operation-scoped grants of 0.25 only (`SELECT,DELETE` invitations · `UPDATE(revoked_at)` refresh_tokens · `DELETE` two_factor_state · `DELETE` login_lockouts · `SELECT` auth_audit_events) — no other access:**
- `refresh_tokens` — SHA-256-hashed, `family_id`, rotation + reuse-detection (revoke whole family on reuse).
- `invitations` — the full onboarding pipeline (Part 0.8): single-use token, email, expiry, pre-assigned panels/projects/role, lifecycle status (`created → sent → accepted → approved / rejected / expired`) + fields captured at accept (`oid`, password hash, profile). **No `users` row exists until approval.**
- `auth_audit_events` — timestamp, user, event type, IP, geo (country/city/asn), device/user-agent, outcome, `jti`.
- `login_lockouts` — **NEW (Part 0.10)**: per-user lockout state (`failure_count`, `last_failure_at`, `locked_until`).
- `two_factor_state` — **ALL 2FA fields (Part 0.10)**: `enabled`, `secret`, `pending_secret`, `pending_expires_at`, keyed by `user_id`.

> **Exclusion honored:** `transaction_reports` stays in rmp; its `project_id` becomes a plain UUID soft-reference (D.4). Fork-side, later phase.

7. **`authorization`** — the central catalog (sections→pages→apis) as the single typed source + a **policy/entitlement resolver** composing L1–L4 into the effective set baked into tokens + a claims-driven guard. Codegen check for catalog↔types drift. (Design at implementer's discretion; 4-layer model fixed.)

# PART I — TOKEN & REQUEST LIFECYCLE (reference)

- **Login (once/session, then ~every 5 min via refresh):** fork → `papi-authority /auth/login` (or `/sso`) with credentials + which panel. papi-authority checks the **panel's enabled auth modes** (Part 0.5), authenticates (password/2FA/lockout), confirms the **panel grant**, reads **L1–L4 for every project the user has**, signs an **RS256 access token** — claims `sub`(userId UUID), `panel`, a `projects` map `{ projectId → {pages, apis} }`, `epoch`, `jti`, `iat`, `exp` (~5 min) — + a rotating refresh token. Returns both → fork → front.
- **Every request (HOT PATH — zero papi-authority calls):** fork verifies the RS256 signature locally against **cached JWKS** (checks `iss`/`aud`/`exp`), reads the active project's entry from the `projects` map by `x-project-id` (rejecting if `x-project-id` isn't in the map), and gates the route. Pure CPU. **rmp keeps serving even if papi-authority is briefly down.**
- **Project switch:** client-side only — the front changes `x-project-id`. The token already carries every project's set; **no new token, no papi-authority call.**
- **Refresh (~5 min, invisible):** fork → `papi-authority /auth/refresh` with refresh token → rotate (reuse-detect) + **re-read current permissions for all projects** → fresh access token. **This is where stale permissions self-correct.**
- **Revocation:** access-control "Unauthorize user" (later) → papi-authority revokes the refresh-token family + deactivates → user fully out within **≤ access-token TTL** (~5 min). No sub-second kill.

# PART J — ONBOARDING FLOWS (one registration, ever)

Identity creation is **once, centrally, in papi-authority**; access is granted **separately, afterward**, by an admin. Two modes share one invitation pipeline; `ONBOARDING_MODE` env flag (default `invite_only`).

**SSO mode (Azure on):**
1. access-control admin clicks **Invite** → enters email (optionally pre-selects panels/projects/role) → papi-authority creates an invitation (single-use token, expiry) and emails the link via ACS.
2. User opens the link → the **standalone join page** → "Continue with Microsoft" → Azure auth → papi-authority verifies the Azure token, **matches email to the invitation**, and stores the captured `oid`/profile **on the invitation** (status `accepted`, pending approval — **no `users` row yet**, Part 0.8) → "Thanks for joining."
3. Admin **approves** (in access-control later; via the identity CRUD API in v1) → the `users` row + panel/project/role grants are created **in one transaction** (pre-assigned grants auto-applied). The user now logs into rmp/cms/dmp with the **same** account — no re-registration anywhere.

**Password mode (Azure off — dev default per Part 0.5, and future fallback):** same pipeline; the join page is **"Set your password"** instead of the Azure button (reuse the `is_sp_reset`/`sp_updated_at` forced-first-login pattern). Admin creates the user in access-control; papi-authority emails the invite; user sets password.

**Uninvited first-login:** under `invite_only` → **rejected, nothing created**. Under `open_sso` → auto-creates an **accepted invitation record** (pending approval) — never a `users` row (Part 0.8).

# PART N — OPEN ITEMS / ASSUMPTIONS FOR THE IMPLEMENTER

- **⚠ CONFLICT FOUND 2026-08-05 — invitation approval cannot be atomic as currently specified.** Part 0.8 requires that approval "creates the real `users` row + all grants **in one transaction**". Part G places `invitations` in the **auth-runtime** group with "access-control DB user = **NO access**". These cannot both hold: approval must *read* the invitation (to copy the captured `oid`/password-hash/profile), *write* `users` + grants, and *mark the invitation approved* — but `users` is writable only by the **console** user while `invitations` is reachable only by the **authority** user, and two DB sessions under different accounts cannot share one transaction (barring XA, which is out of scope). **Resolution to decide at Phase 2 kickoff** (recommendation: grant the console user `SELECT, UPDATE` on `invitations` **only** — no INSERT/DELETE, and no access to any other auth-runtime table — so the whole approval runs as one transaction on the console connection; authority keeps full CRUD on `invitations` for the create/validate/accept steps). Rejected alternatives: moving `invitations` into the identity group (would force the authority user to write an identity-group table, breaking 0.10's clean split); XA/two-phase commit (overkill); non-atomic approval with reconciliation (violates 0.8).
- **✅ RESOLVED 2026-08-06 by decision 0.44 — option (a) was chosen: the console is granted `INSERT` (only) on `auth_audit_events`, so approval runs as one transaction on one connection and the trail stays append-only.** Original entry follows for the record. — **⚠ Invitation-approval audit cannot be atomic — decide at Phase 7.** Decision 0.25 gives the console principal **SELECT only** on `auth_audit_events` (no INSERT), and grants verification confirms it: a console `INSERT` into the audit table is denied. But 0.24 requires approval to create the `users` row + grants and delete the invitation **in one transaction**, with a full audit record written **before** the delete. Those cannot both happen in one transaction, because the audit write must go through the **authority** connection while the approval runs on the **console** connection — two sessions, two transactions. Options for Phase 7: **(a)** grant the console `INSERT` (and only INSERT) on `auth_audit_events`, keeping the property that it can never *edit or erase* the trail while allowing it to append its own actions atomically; **(b)** write the audit event on the authority connection *before* the approval transaction, and emit a compensating `invitation.approval_failed` event if the approval then fails. (a) is simpler and preserves append-only; (b) preserves 0.25 verbatim at the cost of a two-step protocol. Do not implement approval until this is settled.
- **Self-service user data (profile / language / password) has no defined home.** Part 0.11 locks password + invitation management to access-control and forbids it from the fork admin panels, but says nothing about a user updating their **own** preferences (language, timezone, phone, display name) — which every fork's `PATCH /api/user/me` supports today (Part E.2, F.4). Since `users` moves to papi-authority, the forks can no longer serve this locally. To decide before Phase 7.
- **Azure specifics needed at the relevant steps:** Key Vault name/URI + the RS256 key identifier and ACS connection string + sender address stay as **env placeholders** (Part 0.4). Azure AD tenant/client IDs are **per-panel DB config**, seeded with placeholders. None block Phase 1. Dev runs on the local key mode + password login (Part 0.4/0.5).
- **`token_epoch`** column is included but **not enforced in v1** (a no-Redis, no-sub-second-kill decision). It reserves a clean path to near-instant revocation later (compare token `epoch` vs a live value) if requirements tighten.
- **Fork wiring, frontend `users`-block deletion, and the numeric→UUID data migration are explicitly later phases** — do not touch platform-admin repos from this project (see the collaboration rule: never modify fork repos from core work without explicit scope).
- **DB engine: MySQL (decided, Part 0.2).** UUIDv7 stored as `BINARY(16)` or `CHAR(36)` — decide at Phase 2 kickoff (recommendation will be presented then).
